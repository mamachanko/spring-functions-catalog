= JDBC Consumer

A consumer that writes message values to a relational database through Spring Integration's `JdbcMessageHandler`.
It generates an `INSERT` statement or executes SQL supplied in `jdbc.consumer.query`.

== Beans for injection

The `JdbcConsumerConfiguration` auto-configuration provides a `Consumer<Message<?>>` bean named `jdbcConsumer`.
Use `jdbcConsumer` as a qualifier when injecting the consumer.

== Database connection

Configure the database with Spring Boot's `spring.datasource.*` properties, including the URL, username, password, and driver class name if needed.
The database account must have permission to execute the configured SQL.

== Mapping message values

`jdbc.consumer.columns` maps SQL parameter names to SpEL expressions.
For example:

[source,properties]
----
jdbc.consumer.columns=id:payload.id,status:payload.status
----

For a message with the JSON payload `{"id":"C-17","status":"new"}`, this supplies `id` and `status` values.
The shorthand `id,status` tries each name as an expression and then as a property of the payload.
Expressions can also read headers, for example `id:headers['claimId'],status:payload.status`.
An expression that cannot be resolved supplies SQL `NULL`.
The default mapping is `payload:payload.toString()`.

== Inserting rows

When `jdbc.consumer.query` is absent, empty, or blank, the consumer generates an `INSERT` statement from `jdbc.consumer.table-name` and `jdbc.consumer.columns`.
The default table name is `messages`.
For example:

[source,properties]
----
jdbc.consumer.table-name=claims
jdbc.consumer.columns=id,status
----

This executes `INSERT INTO claims(id, status) VALUES (:id, :status)` for each message.
The table must exist and its column types must accept the mapped values.

== Executing SQL

Set `jdbc.consumer.query` to a SQL write statement with named parameters.
Each named parameter must have a mapping in `jdbc.consumer.columns`.
The mapped values are bound as parameters; they are not substituted into the SQL text.
With a configured query, mapping names do not have to match database column names.
The SQL determines the target table; `jdbc.consumer.table-name` is used only for initialization.

For example, this configuration updates a row:

[source,properties]
----
jdbc.consumer.columns=key:headers['claimId'],state:payload.status
jdbc.consumer.query=UPDATE claims SET status=:state WHERE id=:key
----

If no row matches, the consumer does not insert a row.
The consumer does not return query results or affected-row counts.
Database and parameter-binding failures during a synchronous write propagate to the caller.
An idle-timeout flush runs asynchronously; its errors do not return to an earlier consumer call.

=== PostgreSQL upsert

An upsert inserts a row when its key is missing and updates a row when its key exists.
The database selects the action in one statement.
For PostgreSQL, create a table with a primary key or suitable unique constraint:

[source,sql]
----
CREATE TABLE claims (id VARCHAR(40) PRIMARY KEY, status VARCHAR(40));
----

Then configure:

[source,properties]
----
jdbc.consumer.columns=id,status
jdbc.consumer.query=INSERT INTO claims (id,status) VALUES (:id,:status) ON CONFLICT (id) DO UPDATE SET status=EXCLUDED.status
----

Messages for the same `id` replace the stored status.

=== MySQL upsert

MySQL uses a different SQL statement for a table with a primary key or unique constraint:

[source,properties]
----
jdbc.consumer.columns=id,status
jdbc.consumer.query=INSERT INTO claims (id,status) VALUES (:id,:status) ON DUPLICATE KEY UPDATE status=:status
----

The consumer does not translate SQL between database types.
Choose SQL, constraints, and update rules for the target database.

== Batching and initialization

`jdbc.consumer.batch-size` sets the number of messages to collect before a JDBC batch is sent.
The default is `1`.
`jdbc.consumer.idle-timeout` sets the idle time in milliseconds before a partial batch is sent.
The default is `-1`, which disables the idle timeout.
These settings apply to generated inserts and configured SQL.
Buffered messages are held in memory.

By default, the consumer does not initialize the database.
Set `jdbc.consumer.initialize` to the location of a SQL script to initialize a schema.
The value `true` drops and recreates `jdbc.consumer.table-name` with `VARCHAR` columns from the mapping names.
This generated schema has no primary key or unique constraint.
Use a database migration or a custom initialization script for an upsert schema.

== Ordering and repeated messages

The consumer has no built-in event deduplication or version checks.
An assignment such as `status=:status` can tolerate a repeated message, but an update such as `total=total+:amount` applies the change again.
A late event can overwrite a newer value unless the SQL checks a version or another ordering field.

The consumer does not coordinate a database commit with acknowledgement by an external message broker.
A failure after a commit can cause a message to be delivered again.
Choose constraints and SQL that meet the application's requirements for retries and ordering.

== Configuration options

All consumer properties use the `jdbc.consumer` prefix.
See link:src/main/java/org/springframework/cloud/fn/consumer/jdbc/JdbcConsumerProperties.java[JdbcConsumerProperties] for the full property list.

== Tests

The link:src/test/java/org/springframework/cloud/fn/consumer/jdbc[test suite] covers generated inserts, configured SQL, and PostgreSQL and MySQL upserts.
The upsert tests require Docker and run with the module's `check` task:

[source,bash]
----
./gradlew :spring-jdbc-consumer:check
----
